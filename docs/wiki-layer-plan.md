# Anamnesia → LLM Wiki: Evolution Plan

Status: **planning, not building**. Captured 2026-05-26 after a three-agent
design review. Implementation deferred to a future session.

## 0. Why this exists

Karpathy's "LLM Wiki" pattern (https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
is the same problem Anamnesia solves with a sharper framing:

> "The LLM incrementally builds and maintains a persistent wiki — a
> structured, interlinked collection of markdown files that sits between
> you and the raw sources. … The cross-references are already there. The
> contradictions have already been flagged."

His three layers map onto our existing architecture:

| Karpathy | Anamnesia today |
|---|---|
| Raw sources (immutable) | `sources` table, raw_content TTL 7d |
| The wiki (mutable, LLM-maintained) | `facts` / `experiences` / `entities` / `edges` |
| Schema (CLAUDE.md / AGENTS.md) | Hardcoded Go + extractor prompt |

The technical bet is different: Karpathy stores the wiki **as markdown
files**; Anamnesia stores it **as typed rows**. Both are correct for their
target users. We want both for our target users — typed storage for the
agent (Claude Code via MCP), markdown view for the human (Obsidian /
VS Code / `cat`).

The reviewer's reframing is load-bearing:

> *"Entity pages aren't the memory; they're the rendered memory."*
> *"Anamnesia is codebase + compiler + linter + indexer. The markdown
> vault is the source view, typed tables are the compiled IR, lint
> workers are the type-checker, retrieval is the index."*

Use this language in the implementation and in user-facing docs.

## 1. What we are adopting from Karpathy

| Gap | Status today | Plan |
|---|---|---|
| **Entity pages** | We have `entities` rows; no synthesized canonical view | Build the renderer; one markdown page per (kind, name) |
| **Markdown vault sync** | API-only, opaque | Push-dominant DB → vault; per-user partitioning |
| **Lint workers** | `decay` recomputes relevance only | Add contradiction / stale / orphan checks |
| **Filed answers** | Session-end folding only | `/v1/retrieve?file=true` persists synthesis as experience |
| **Schema-as-text** | Hardcoded | Extend `.anamnesia.toml` *and* read `CLAUDE.md` / `AGENTS.md` |

## 2. Agent discussion summary

Three agents argued the design. They disagreed sharply on scope, agreed
on philosophy.

**The architect** proposed the full system: a `vaultsync` worker that
tails `audit_log`, debounces writes per file, renders entity pages
through a new `internal/synth/` package, supports an opt-in `--pull`
mode with frontmatter-whitelisted edits, and ships ~2,700 LOC.

**The skeptic** blocked bidirectional sync outright — *"the moment a
markdown file exists on disk that an LLM-driven worker writes and a
human edits in Obsidian, you have a distributed system across two
stores with no transactional boundary"* — and recommended starting
with a one-shot `anamnesia dump --markdown` subcommand plus
`GET /v1/entity/{id}`, ~5% of the architect's code.

**The Karpathy-fidelity reviewer** confirmed the proposal maps cleanly
to the gist's three operations (ingest / query / lint) and flagged one
divergence to fix: *"splitting extractor rules into `.anamnesia.toml`
while `CLAUDE.md` already exists in every project re-fragments the
surface Karpathy was deliberately consolidating. Fold (E) into the
existing `CLAUDE.md` / `AGENTS.md` convention or accept that we've
quietly invented a fourth layer he didn't have."* Also surfaced two
missing pieces the architect's design covers in practice but should be
explicit in v2: **concept / comparison pages** and a single **overview
page**.

**Resolution.** Ship the skeptic's narrow shape first. Earn the
architect's full design with user demand, not speculation. Adopt the
reviewer's schema-location pushback verbatim.

## 3. Source-of-truth contract

The single most important decision, locked here so v1 doesn't drift:

1. **Postgres is the source of truth.** Always.
2. **The vault is a derived view.** It is read-only for humans in v1.
3. **Every generated file carries a banner**:
   ```
   <!-- generated by anamnesia; edits will be overwritten -->
   ```
4. **A content hash per row is persisted** in DB (`facts.vault_hash`,
   `experiences.vault_hash`, `entities.vault_hash`) so a `reconcile`
   subcommand can detect drift and re-render.
5. **No filesystem watcher.** macOS + Docker bind mount + iCloud =
   pain. Re-render on explicit command in v1.
6. **No write-back** in v1. The architect's frontmatter-whitelist
   `--pull` is deferred to v3 once we have user pull for it.

This is the skeptic's "own it" recommendation, made architectural.

## 4. File layout (per-user vault)

```
vault/
  <user-slug>/
    _index.md                       # auto-generated table of contents
    _overview.md                    # single "what does this user know" summary
    _lint.md                        # global lint report
    entities/
      person/<slug>.md              # one file per (kind, name)
      project/<slug>.md
      tool/<slug>.md
      concept/<slug>.md             # v2: concept pages
    facts/
      <project-slug-or-_user>/      # FactScope partition
        <fact.key>.md               # dots in key preserved
    experiences/
      YYYY/MM/YYYY-MM-DD--<title-slug>--<uuid8>.md
    skills/
      <name>.md
    answers/                        # v2: filed retrieve responses
      YYYY-MM-DD--<question-slug>--<uuid8>.md
```

Rules:
- One file per `(kind, name)` entity or per fact key. No bundling.
- `uuid8` suffix on experiences / answers prevents collisions when titles
  repeat.
- Per-user partitioning matches Anamnesia's "no multitenancy, single owner"
  rule. No shared subtrees.

## 5. Entity page schema

Frontmatter is YAML, body is markdown with `[[wiki-links]]`. Citations
use `[f:<uuid>]` / `[e:<uuid>]` resolving to `anamnesia://fact/<uuid>`
URIs the CLI can open — not deep file paths, since rows move between
files on entity rename.

```markdown
---
anamnesia:
  id: <uuid>
  kind: project
  name: anamnesia
  scope: { user_id: <uuid>, project_id: <uuid|null> }
  updated_at: 2026-05-22T14:02:11Z
  synthesis_rev: 14
  synth_hash: <sha256>
  fact_ids: [<uuid>, ...]
  experience_ids: [<uuid>, ...]
  edge_ids: [<uuid>, ...]
tags: [active]
pinned: true            # user can set; controls immediate-resync
stale: false            # set by lint
orphan: false           # set by lint
---

<!-- generated by anamnesia; edits will be overwritten -->

# Anamnesia

> Local-first long-term memory for AI agents. *(synthesised 2026-05-22)*

## Synthesis

Anamnesia is a Go binary + Postgres + MCP endpoint owned by [[person/floh]].
It extracts durable bits from chat via [[tool/claude-code]] hooks…

## Facts

- **editor.preference** = `nvim` <sup>[f:a1…](anamnesia://fact/a1...)</sup>
- **deploy.target** = `docker-compose` <sup>[f:b2…](anamnesia://fact/b2...)</sup>

## Recent experiences

- 2026-05-22 — [[experiences/2026/05/2026-05-22--debugging-rrf-fusion--c3…|debugging RRF fusion]] (success)

## Edges

- `owns` → [[person/floh]]
- `depends_on` → [[tool/pgvector]], [[tool/postgres]]

## ⚠ Lint

(populated by lint worker; absent when clean)
```

The `[[wiki-links]]` are load-bearing per the reviewer — Obsidian's
graph view depends on them, and they're what makes this a *wiki* and not
just a dump.

## 6. Phased implementation

Order is locked. Each phase produces a complete, shippable thing.

### v1 — Render on demand (the skeptic's shape)

**Goal:** prove the value with the smallest possible surface.

- New subcommand `anamnesia dump --markdown [--user <slug>] [--out ./vault]`.
- New package `internal/vaultrender/` — pure functions, no goroutines,
  no audit-log tailing.
- Renders entities, facts, experiences, skills per §4 layout.
- Banner on every file. No watchers. No write-back.
- Content hash columns added to `facts` / `experiences` / `entities` via
  a new goose migration (`internal/store/migrations/0004_vault_hash.sql`).
- New endpoint `GET /v1/entity/{id}` returns JSON (the rendered-markdown
  view is the dump's job; the API stays structured).
- Entity pages render *without* LLM synthesis — just a deterministic
  layout of the typed data. Synthesis lands in v2.
- New CLI flag `anamnesia reconcile --vault ./vault` walks the tree,
  re-renders any file whose stored hash mismatches, prunes orphan files.

LOC target: ~600 + 200 test. No worker, no LLM call.

### v2 — Synthesis + lint + filed answers

**Goal:** add the Karpathy primitives that need LLM in the loop.

- New package `internal/synth/`. Hourly sweep (cadence
  `ANAMNESIA_SYNTH_EVERY=1h`) over entities with
  `updated_at > last_synth_at`. Immediate path for entities flagged
  `pinned: true` in `entities.props`.
- `synth.Synthesiser` interface:
  ```go
  type Synthesiser interface {
      Synthesise(ctx context.Context, e anamnesia.Entity,
          facts []anamnesia.Fact, exps []anamnesia.Experience,
          edges []anamnesia.Edge) (Synthesis, error)
  }
  type Synthesis struct {
      Paragraph       string
      Contradictions  []Contradiction
      StaleClaims     []uuid.UUID
      InputHash       string
  }
  ```
- Deterministic stub when `ANAMNESIA_LLM_PROVIDER=stub` — synthesis becomes
  *"N facts, M experiences, K edges"* so the wiki compiles offline.
- Lint operations:
  - **Contradictions**: produced inline by `synth` (LLM compares fact
    values with the same key). Rendered as `## ⚠ Contradictions` in the
    entity page.
  - **Stale claims**: deterministic — `fact.valid_to IS NOT NULL` or
    `experience.relevance < 0.1`. Frontmatter `stale: true`.
  - **Orphan pages**: entity with `fact_count + experience_count +
    edge_count == 0` after 7d. Frontmatter `orphan: true`. No auto-delete.
- `_lint.md` rollup per user — greppable view of every `stale: true` /
  `orphan: true` flag.
- **Filed answers** — extend `/v1/retrieve` and the MCP
  `anamnesia_search` tool with optional `file: bool`. When set:
  1. Compose the synthesis as today.
  2. Insert a row in `experiences` with `kind=strategy`,
     `abstraction=2`, `meta.filed_from_query="…"`,
     `provenance.hit_ids=[…]`.
  3. `anamnesia dump --markdown` (or v3's sync worker) renders it under
     `answers/<date>--<slug>--<uuid8>.md`.
  Opt-in only. Auto-filing pollutes the embedding space.
- **Concept pages and overview page** (the reviewer's missing pieces) —
  add a `kind=concept` row variant; render `_overview.md` from a fixed
  top-K of facts + entities per user.

LOC target: ~1,000 + 300 test.

### v3 — Push-dominant sync worker (the architect's shape)

**Goal:** make the vault live. Only if v1+v2 see adoption.

- New package `internal/vaultsync/`. Tails `audit_log` (already exists per
  `pkg/anamnesia/types.go`). Every committed row → enqueue render task.
  Debounced 5s per file. Cadence env
  `ANAMNESIA_VAULTSYNC_EVERY=5s`.
- Replaces the v1 `anamnesia dump` for users who want live updates.
  `dump` remains for one-shots / CI.
- Optional `anamnesia sync --pull` walks the vault, diffs frontmatter
  against DB. **Only a whitelist round-trips:** `tags`, `pinned`, plus
  the freeform `## Notes` section on entity pages (stored in
  `entities.props.user_notes`). Body text of facts/experiences is
  read-only.
- No filesystem watcher. Pull is on-command.

LOC target: ~1,100 + 400 test. This is the bulk of the work.

### v4 — Schema-as-text

**Goal:** let users customize without recompiling.

Per the reviewer's pushback, **do not invent a new schema file**. Extend
existing surfaces:

- Read `CLAUDE.md` / `AGENTS.md` from the project root if present. Parse
  a fenced `\`\`\`anamnesia` block:
  ```
  \`\`\`anamnesia
  extractor:
    bias: durable_only          # default; or `liberal` for benchmarks
    forbidden_keys:
      - user.demographics.*     # negative-extraction examples
  lint:
    stale_after: 90d
  vault:
    entity_kinds: [person, project, tool]
  \`\`\`
  ```
- Extend `.anamnesia.toml` (already exists per `anamnesia init`) with
  matching keys. Both sources merge; `CLAUDE.md` wins on conflict so the
  agent's view of schema matches Anamnesia's.

LOC target: ~300 + 100 test.

## 7. What we are explicitly NOT doing in v1

These were proposed, considered, blocked. Recording the decisions so they
don't get re-litigated in a future session:

- **No bidirectional sync** in v1 (skeptic blocked). User edits to
  generated markdown files are not preserved.
- **No filesystem watcher.** Re-render is explicit (`anamnesia dump`) or
  worker-driven (v3 only).
- **No markdown-to-typed parser.** Round-tripping LLM-extracted prose back
  into rows is a research problem, not a v1 feature.
- **No cross-user vault subtrees.** Each user's vault is isolated;
  shared-team views are a UI problem, not a storage one.
- **No automatic filed answers.** Filing is opt-in via the `file: true`
  flag on `/v1/retrieve`.
- **No new schema file.** Extend `CLAUDE.md` and `.anamnesia.toml`; don't
  introduce a third surface.

## 8. Open questions for the implementation session

To answer before starting v1:

1. Should `anamnesia dump` be a hook target (renders on `SessionEnd`) or
   purely manual? *Lean: manual for v1, hook in v3 once sync exists.*
2. Vault directory default location — `./vault` next to the project, or
   `~/.anamnesia/vault/<user>/`? *Lean: `--out` flag, no default.*
3. Do we render even when `ANAMNESIA_LLM_PROVIDER=stub`? *Yes — v1 has no
   LLM call; v2 has a deterministic stub.*
4. Migration path: do existing rows get backfilled into the vault on the
   first `dump` call, or do we require a `reconcile`? *Lean: `dump`
   always renders everything; `reconcile` is just `dump` + prune.*
5. Naming: "the wiki" vs "the vault" vs "the render"? *Use **vault** in
   code (matches Obsidian) and **wiki** in user docs (matches Karpathy).
   Internal types use neither — `vaultrender.Render…`.*

## 9. How we are better than the gist, not just compatible

Per the reviewer's framing:

> *Anamnesia is codebase + compiler + linter + indexer. The markdown
> vault is the source view, typed tables are the compiled IR, lint
> workers are the type-checker, retrieval is the index.*

Karpathy ships the codebase. We ship the codebase plus the toolchain.
Specifically:

- **Hybrid retrieval** (pgvector + tsvector + RRF) over a markdown dir
  doesn't exist for him — that's our compiler-output index.
- **PII scrub at ingest** is impossible with a flat-file vault; we own it.
- **Bitemporal graph** (`valid_from` / `valid_to`) is impossible with a
  flat-file vault; we own it.
- **Multi-user** is impossible cleanly with a flat-file vault; we own it.
- **MCP endpoint** means Claude Code calls us directly, no editor
  required. Karpathy's pattern requires an LLM client that knows how to
  edit files in a vault.

The path to "better than Karpathy" is not to *become* his design — it's
to make his design's outputs available as a view over ours, and to keep
the structured backend for everything that needs it.
